The character keeper that isn't yet the game table

Agent Resources is a well-built companion app with an unusually disciplined engineering culture and a core loop that leaks at every seam where the product touches the place its players actually live: Discord.

Read of the product

The surface area here is real and it is not thin. Characters have a five-step guided wizard and an expert form, two rules versions, level-up, offscreen missions, import/export, death, and public sharing. Classes carry gear, abilities, stat spreads, player-created variants, version families, and a whole unlock-code economy. There is a gated PDF library with temporary and free-access tiers, a looking-for-game board with join requests and a calendar, collaborative mission logs with editor invites and merge, a shareable virtual-party stat calculator, badges, public profiles, a dynamic navbar, a CMS, a sitemap, an agent API, and Discord account linking. That is a lot of product for one maintainer.

The engineering discipline behind it is genuinely above what this category usually gets: every feature since June ships as a spec commit, then a plan commit, then the implementation; there are four test tiers including a real Chromium end-to-end suite; there is a migration rehearsal script that replays pending migrations against a copy of production. The 2026-08-05 end-to-end report found twenty defects and, checking the tree today, the critical ones are fixed — silent class reassignment on save, the dead Pages CMS, the export links that never downloaded. That is a team that finds its own bugs and closes them.

So the problem is not build quality. The problem is that the product's shape has been set by what was tractable to build rather than by where the player's attention actually is — and for a tableless RPG, the player's attention is in a Discord voice channel, on a phone, at 8pm on a Thursday.

The core loop, and where it leaks

Discover

Someone posts a link in a Discord server. Public characters, missions, classes and profiles are server-rendered and in the sitemap.

There is not a single Open Graph or Twitter card tag in the codebase. Every link pasted into Discord — the one channel this community runs on — renders as a bare grey URL.
Onboard

Sign in with Discord, email, or magic link. A path-aware checklist asks "have you played before?" and branches to Quickstart or code redemption.

This is good work and recently shipped. Keep it.
Create

The wizard, or expert mode. Strongest single feature in the app.

Deep, considered, and clearly the thing the most care went into.
Find a game

The onboarding checklist's final step points at /lfg.

If the board is empty, the new player's journey ends there with "Check back soon." No fallback, no way to register interest, no signal to anyone that a player is waiting. Nobody is told a join request arrived. The host learns only by returning to the page and clicking "Show".
Play

The session happens somewhere else entirely.

The Library's first and most prominent box hands the player a printable PDF character sheet. At the moment of play the app sends users away from itself.
Log

Someone opens the mission form and types in the title, date, conduit, and every participating character by hand.

The LFG post already knows all four. It computes the approved roster and its combined party stats to render the page, then throws that away. There is no "log this game" action anywhere.
Level

Completed missions drive level-up, which is the reason to come back.

The whole retention engine depends on the manual step above actually happening after a tiring three-hour session.
Every stage that requires the product to reach a player, rather than wait for one, is missing. That is one gap, appearing six times.

What I would do, in order

01

Make the product talk to Discord

RetentionEffort: mediumMost of the plumbing exists

There is no notification of any kind in this application. Not email, not Discord, not in-app. A host is never told a player asked to join. A player is never told they were approved. Nobody is reminded that a game they joined is tomorrow. Nobody is told their character was added to a logged mission. For a product whose central object is a scheduled event with other people, this is the gap that matters more than every other item on this list combined.

What makes this a near-term project rather than a rebuild is that the hard parts are already built. Discord is a sign-in method, profiles.discord_id is stored and uniquely indexed, there is a bot-linking flow with long-lived agent tokens, and the agent API already exposes the entire LFG surface. The missing piece is a dispatcher and five event types.

Verified

No match for notification, webhook, email-send, or Discord API dispatch anywhere in routes/, services/, models/, or util/.

Ship first: join request received, join request approved, game starts in 24 hours. Those three carry most of the value.

02

Close the LFG-to-mission gap

RetentionEffort: smallData already loaded

Mission logging is the engine of progression, and progression is the reason a character is worth returning to. Right now logging is the highest-friction, most redundant data entry in the app, and it lands at the point of lowest energy — the end of a session.

Verified

routes/lfg.js:107-120 builds the approved character roster and party summary for the post page. views/lfg-post.handlebars renders party stats and calendar export buttons — but nothing that creates a mission. The mission form asks for the title, date, conduit, and characters again from scratch.

Add one button on a past-dated LFG post: Log this game. It opens the mission form pre-filled with the post's title, date, conduit, and every approved character. The Conduit writes the summary and saves. That is the difference between a log that happens and a log that doesn't.

03

Add link previews

GrowthEffort: hoursHighest ratio on this list

The codebase contains zero og: or twitter: meta tags. Public characters, classes, missions and profiles all render server-side for signed-out visitors and are all in the sitemap — the content is share-ready and the sharing is not. Every character someone shows off in Discord is currently an unstyled URL that nobody clicks.

Title, description, and an image per shareable type. Characters and classes already carry image_url with crop data, so there is art to use. This is an afternoon of work that turns every proud player into a distribution channel, and it is the only item here that grows the top of the funnel rather than plugging the bottom.

04

Decide whether the app is the sheet at the table

PositioningEffort: largeAnswer this before building

This is the strategic question the roadmap has not been asked to answer. Today the character page is a 400-line reference document: boxes of stats, gear, perks, and recent missions. There is no HP or condition tracking, no dice, no in-session state, no compact view for a phone held in one hand during a voice call. And the Library's most prominent element is a link to a printable PDF sheet.

If players print that sheet, the app is a character creator they visit twice per character. If the app is the sheet, it is open for three hours every session and it becomes the place the group's habits form. Those are different products with different retention curves, and the second one is the one that becomes must-use.

The version worth prototyping is small: a "play view" route on an existing character — large type, abilities and gear as the primary content rather than an afterthought, whatever counters Enclave's rules actually need, and nothing else on screen. Put it in front of six players for one session before building anything more.

05

Instrument the funnel

FoundationEffort: smallEverything above is a guess without it

There is no analytics, no event tracking, and no product metrics anywhere in the codebase. The team ships with real rigor — spec, plan, implement, four test tiers — and then has no way to know whether anything worked.

Concretely unanswerable today: what share of signups create a character; what share of wizard starts reach step five and which step loses them; how many LFG posts ever receive a join request; how many played games get logged; how many players return in week two. Every prioritization argument, including this document, is currently reasoned from code rather than from behavior.

A privacy-respecting page-view tool plus a dozen named server-side events would close it. Do this before item 4, so the play-view experiment produces evidence instead of an opinion.

06

Give the Conduit a reason to be here

Supply sideEffort: medium

Game masters are the scarce side of every tabletop community — one Conduit unblocks four or five players. In this product a Conduit gets a checkbox on an LFG post, mission editor rights, and a conduit_briefing text field that renders only on their public profile. The party stat summary on the post page is a genuinely good start and points the right way.

What is missing is anything for preparing or running a session: no adversary or NPC records, no session notes, no place to keep the thing you wrote last week, no surface built around "I am running this game in ten minutes." The player side has a five-step wizard; the Conduit side has a checkbox.

The cheap version is a run screen off the LFG post: the roster with each character's stats expanded, the party summary, private Conduit notes for the game, and the "log this game" button from item 2 sitting at the bottom.

07

Fix the two live LFG defects before promoting the board

CorrectnessEffort: hoursBoth still present

A player cannot see that a game already has a Conduit. models/lfg.js:25-38 derives host_id from the join requests, but row-level security shows a non-owner only their own requests — so the derivation finds nothing and overwrites the correct host_id the row actually carried with null. Every public post with a Conduit displays "Conduit needed" to everyone else. A player volunteers, the server rejects it, and because that path returns a bare string that the error handler has no branch for, they read "Join failed" on a 500. This is a one-branch fix in applyConduitMeta and it is sitting in the single funnel that matters most.

Back button blanks the page. The August end-to-end report's finding 2 is still open: util/auth.js:41-44 answers an htmx history-restore request with a 200, an HX-Redirect header, and an empty body, which htmx swaps into <body> as zero bytes. There is no HX-History-Restore-Request handling anywhere in the tree. A signed-in user who browses a dozen pages and holds Back gets a permanent white screen; users with blocked local storage hit it on the first Back, every time.

Root cause worth naming

Both symptoms, plus the export workaround and the app's total dependence on JavaScript for a signed-in first paint, trace to authentication by a JS-written Authorization header rather than a cookie. Moving to cookie-based sessions would delete a class of product bugs rather than another instance of one. That is the one architectural rework I would argue for on product grounds — but after items 1 through 3, not before.

08

Rebalance the roadmap away from entitlements

ProcessEffort: none — a decision

All seventeen tickets in .tickets/ are engineering tickets — architecture, tooling, test coverage, runbooks. Not one describes a player outcome. The backlog has no product half, so the roadmap is being set by whatever the last spec document happened to be about.

And what those specs have been about is unlock plumbing. Of the last ten shipped features, six are access-control work: class-list partitioning by release state, library version collapse, an admin unlocks dashboard, temporary unlock expiry display, admin-override badging, and granting classes from owned PDFs. That is a great deal of energy in the entitlement layer relative to the play layer.

If unlock codes are carrying real revenue, some of that is correct and this is a ratio question rather than a wrong-direction question. But entitlement work only pays off when there is something worth being entitled to, and right now nothing in the pipeline is making the play experience better.

What I would not touch

The character wizard. It is the best thing in the product and it is finished enough. Resist adding modes.

Social features. No follows, no comments, no feeds, no leaderboards. Community features amplify a loop; they do not create one. Every one of them built before item 1 lands in an app nobody has a reason to open.

The engineering discipline. The spec-then-plan-then-implement rhythm, the four test tiers, the migration rehearsal — this is why the product is trustworthy, and it is not what is holding it back. Point it at different targets rather than slowing it down.

Bulma and htmx. The stack is fine. Nothing on this list is blocked by it. The one exception is the header-auth choice in item 7, which is a bug class, not a framework.

The one-line version

Agent Resources is three small projects away from being the thing an Enclave group opens on game night instead of a PDF and a Discord thread: tell people when something happens, turn the game they scheduled into the mission they played, and make every link they share look like something worth clicking. Everything else on this list is downstream of those.
